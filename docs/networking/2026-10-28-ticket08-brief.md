# Ticket 08: 16 席负载与故障验收

## 基线与边界

- 从 `ticket08/cloud-16-seat-20261028` 独立分支工作；该分支以本地验收后的 Ticket 07 提交为起点。
- 只提交、推送这个独立分支。不要修改、提交、推送或合并 `develop`、`master`、`main`、`refactor/reusable-components`。
- 本地 Ticket 07 和云端 Ticket 08 并行推进；云端成果由本地检查后再决定是否合并。
- 保留 `res://scene/main.tscn` 单机入口。若发现兼容入口需要收缩，先给出证据和独立改动，不破坏现有单机玩法。

## 目标

让独立 PvP 入口 `res://scene/pvp_main.tscn` 在最多 16 个席位下稳定收敛；移动、命中、格挡、物品、星星和整局胜负仍由房主裁决。当前 20 Hz 移动快照已剥离完整 combat 并改为精简字段，但只验证了三人包低于一次观测到的 1392 字节 ENet MTU，不能据此宣称 16 人可用。

## 实施与验收

1. 量测 1、4、8、16 人的实际移动快照与可靠战斗包大小、频率和客户端收敛情况。不要只测序列化估算；至少用真实 ENet 多进程测试一组较大人数，并记录机器与时长。
2. 修复超过 MTU 的高频包：可使用分包、局部视野、压缩或其他有证据的方案。保留每个玩家的稳定 ID、tick、revision 和本地输入确认；客户端不能把不同 tick 的不完整分包误认成完整世界状态。
3. 验证满 16 席时拒绝第 17 人；30 秒保留席位中的玩家能以原身份重连；到期后新玩家可以占用座位但取得新的永久玩家 ID。
4. 验证中途加入不增加已冻结的星星数量；16 人开局最多 4 颗星星，撤离点数量由地图决定。房主离开时房间结束，客户端停止提交命令。
5. 覆盖超时、全部星星消耗、无人继续参赛三种整局结束，及胜者观战。任何对局结束后的新加入不得产生无角色的幽灵身份。
6. 为发现的负载和故障边界添加有意义的 Godot 测试，运行并记录结果。云端若无 Godot 4.7 可执行环境，先尝试在云端配置与项目匹配的运行环境；若仍无法运行，明确标记“未在云端验证”，提交可由本地运行的测试，不声称已通过。
